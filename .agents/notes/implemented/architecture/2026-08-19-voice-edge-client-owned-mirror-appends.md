# Agent Note: Voice Edge mirror appends are client-delivered

Status: implemented

English | [中文](2026-08-19-voice-edge-client-owned-mirror-appends.zh.md)

## Problem

The bridge's first API coupled recording to transport. `/session/sync` accepted a `messages` projection and appended the `voice-edge/sync` event itself, re-extracting user text from the raw client history with a second, simplified parser beside the relay's envelope-aware one. A client message shape only the first parser understood (Continue's part arrays) produced sync events with empty text — an empty user bubble in the Web mirror — while the actual model request, built from the relay's cleaned final prompt, was fine. `/model/event` and `/turn/finish` were separate append endpoints, and `/tool/execute` recorded the tool pair, so log authorship was split across four routes with no statement of who owns which event.

## Decision

Voice_edge.py owns the information flow; the plugin is passive. `/session/bind` only binds keys, creates/resumes the agent, and returns tool schemas — it records nothing. One endpoint, `/event`, appends any event the client explicitly delivers: `voice-edge/sync` (whose `messages` carries the user's fresh turn text — `PreparedTurn.user_text`, the relay-extracted body of the submitted prompt; empty on tool-result continuations and attachment-only turns, which mirror no user message), `voice-edge/model-event`, and `voice-edge/finish` (which also dispatches the durability flush). `/tool/execute` is unchanged: execution belongs to the harness, so it keeps recording the `voice-edge/tool-call`/`voice-edge/tool-result` pair at the point that owns the facts. Each event class has exactly one author — stream content from the client, execution outcomes from the executor — and no parse of client messages exists on the harness side at all. Event types and payloads are unchanged, so ui-voice-edge, blankness, and restart adoption are untouched. Mirror texts are stored verbatim: every earlier length cap (4,000 chars per sync message, 16,000 per event text, the 50-message projection bound, and the client-side prompt truncation) is deleted — `config.maxBodyBytes` at the HTTP wire is the single size bound, so the log cannot show less than what arrived.

## Alternatives considered

**Fix the second extractor to match the relay's.** Rejected: two parsers over the same bytes drift by construction; every new client envelope would be a mirror bug until re-taught.

**A dedicated `/user/message` endpoint beside unchanged sync.** Rejected: it leaves the misleading `messages` projection on the wire and adds a fourth append route; one `/event` with a `type` discriminant states the contract in a single place.

**Have the client deliver tool events too, making every append client-owned.** Rejected: the executor already holds the call arguments, result, timing, and error state; making the client restate them creates a second source of truth for the one event class the harness genuinely owns.

## Consequences

The mirror can no longer diverge from what the model received: the user bubble is the relay-extracted turn body — the same first-extractor output the submitted prompt carries — minus transport framing. Mirrored assistant steps render through the shared assistant-Markdown primitive (the literal-text primitive was a contract violation of that primitive's own split), and the renderer's image gate admits well-formed inline `data:image/*;base64` rasters — model-generated images arrive as base64 markdown — while SVG (script-capable document) and truncated payloads (a stream cut mid-image leaves a dangling partial base64 group) fall back to alt text. The user's own inline images ride the m365 attachment egress (uploaded for the vision model), so the extracted turn text loses them; the mirror re-embeds them as markdown data URIs on fresh turns only — `PreparedTurn.fresh_user_turn` is the gate, because attachment collection re-reads the same latest user message on every tool-result continuation and would otherwise re-mirror stale images every round — and the user bubble renders Markdown for the same reason as the assistant rows. That framing exclusion is deliberate: the harness tool catalog necessarily enters every model request as `<tool_use_instructions>` prompt text (browser models have no native function calling; the instruction block is the tool channel, and voice_edge.py performs the injection from the bind catalog), but it is per-turn boilerplate reconstructable from the harness's own catalog, so recording it in every user bubble would bury the user's question under a wall of tool XML — the readable mirror records conversation content, not transport. Bind is idempotent and content-free, so a re-bind cannot duplicate or corrupt a turn. The client's failure stance (fail-open, log-and-drop on every mirror tap) is now the only stance that can lose a log row — a mirror outage never touches the request path, and the harness never silently drops delivered content. Known residual: a turn that binds but crashes before the user-message tap leaves a session with no `voice-edge/sync`, which stays `blank: true` — the same visibility a never-started conversation has.
